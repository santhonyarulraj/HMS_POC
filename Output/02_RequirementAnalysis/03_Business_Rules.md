# 03 — Business Rules

Rules are grouped by module. Each is traceable to its source feature ID(s). "Known gap" rules are current, *code-verified* as-built behavior that deviates from the ideal specification — they are rules an automated test must respect (as actual system behavior), not defects to silently work around.

---

## A. Login — Business Rules

| # | Rule | Source |
|---|---|---|
| BR-L-01 | Exactly four system roles exist: admin, doctor, receptionist, pharmacist. Custom role creation is **not** supported. | HC-USR §1.4, repeated in Assumptions #1 — **see `06_Gaps_and_Risks.md` for a direct conflict with the Role Matrix document on this rule** |
| BR-L-02 | A deactivated account cannot log in, regardless of correct credentials. | HC-USR-001 AC5 |
| BR-L-03 | An account flagged for forced password reset is redirected to Change Password before the dashboard opens, on every login until the flag clears. | HC-USR-001 AC6, HC-USR-010 AC4 |
| BR-L-04 | If 2FA is enabled on the account, or enforced for the account's role, the second factor is required before the session is granted — no exceptions. | HC-USR-001 AC7 |
| BR-L-05 | Login attempts are rate-limited to 5 per minute per source address. | HC-USR-001 AC9, NFR-003 |
| BR-L-06 | The invalid-credentials error message never discloses whether the username or the password was wrong. | HC-USR-001 AC10 |
| BR-L-07 | Logout invalidates the session **server-side** immediately; a replayed (already-invalidated) session credential is refused on any subsequent request. | HC-USR-002 AC2/AC5, NFR-004 |
| BR-L-08 | Password complexity policy (applies to every password-set operation: change, admin temp-set, reset-with-code): minimum 8 characters, ≥1 uppercase, ≥1 digit, ≥1 special character. | HC-USR-010/011/013, §3.3 |
| BR-L-09 | Changing your own password clears any forced-reset flag on the account. | HC-USR-010 AC4 |
| BR-L-10 | **Known gap:** a password change does **not** invalidate the user's other active sessions in the current build — a stolen session survives a password reset until it naturally expires. | HC-USR-010 AC6, §3.2 Gap 2 |
| BR-L-11 | Forgot-password codes are delivered by email only — never SMS, WhatsApp, or a clickable link. | HC-USR-012 AC4, Assumptions #4 |
| BR-L-12 | Forgot-password codes are valid for 15 minutes and usable exactly once. | HC-USR-012 AC5, HC-USR-013 AC2 |
| BR-L-13 | The forgot-password confirmation message is identical whether or not the submitted username/email actually exists (no account enumeration). | HC-USR-012 AC6 |
| BR-L-14 | 2FA setup is not complete until the user proves possession of the paired app with a valid 6-digit code. | HC-USR-014 AC3 |
| BR-L-15 | 2FA issues exactly 8 single-use backup codes at setup; each is consumed the moment it is used and cannot be reused. | HC-USR-014 AC5, HC-USR-015 AC3 |
| BR-L-16 | TOTP codes are accepted with a tolerance of one 30-second time-step either side of the server's current step (effective ~90-second window), to absorb clock skew. | HC-USR-015 AC2, Assumptions #5 |
| BR-L-17 | 5 consecutive failed 2FA attempts locks the account for 15 minutes. | HC-USR-015 AC5, NFR-003 |
| BR-L-18 | Default 2FA enforcement: **admin = ON**; doctor, receptionist, pharmacist = **OFF**. | HC-USR-017 AC4 |
| BR-L-19 | Session credential (JWT) is held only in a secure, httpOnly, `Secure`, `SameSite=Strict` cookie — never readable by browser-side scripts. Only non-sensitive display data (user object, permission map) is held in script-accessible storage. | NFR-001 |
| BR-L-20 | Passwords are stored only as one-way hashes (bcrypt, cost factor 12); plain text is never stored, logged, or returned by any endpoint. | NFR-002 |
| BR-L-21 | **Known gap:** account creation (HC-USR-004, out of core scope but relevant if staff-account setup is needed for test-data provisioning) is currently callable **without authentication** — a critical, unresolved security gap. | §3.2 Gap 1 |

## B. Patient Registration — Business Rules

| # | Rule | Source |
|---|---|---|
| BR-P-01 | UHID format is fixed: `PAT` + `YYMM` + 4-digit sequence, auto-generated by the system, unique per facility. Never user-entered. | HC-PAT-001 AC9, Assumptions #1 |
| BR-P-02 | In the **Full Wizard**, only First Name, Last Name, and Phone are truly mandatory to complete registration — every other field across all 7 steps is optional. | HC-PAT-001, UI Schema (Table 7) |
| BR-P-03 | In the Full Wizard, the user cannot advance past a step while a mandatory field on that step is invalid. | HC-PAT-001 AC10 |
| BR-P-04 | **Duplicate-phone handling differs by design between flows** (explicitly confirmed, not a defect): the Full Wizard *warns* and allows override ("Continue Anyway") because family members may legitimately share a phone; Quick Registration *blocks* outright and hands back the existing patient. | HC-PAT-017, HC-PAT-002 AC3, Assumptions #3 |
| BR-P-05 | Quick Registration mandatory fields: First Name, Last Name, Phone. DOB and Gender are optional. | HC-PAT-002, UI Schema (Table 10) |
| BR-P-06 | Emergency Registration mandatory fields: Patient Name (the literal value "Unknown" is explicitly permitted) and Chief Complaint. Phone is optional — unconscious/unknown patients can be registered with zero contact details. | HC-PAT-003 AC2/AC3, Validations (Table 14) |
| BR-P-07 | Emergency Registration defaults Triage Priority to **P2** when not specified. | HC-PAT-003, UI Schema (Table 13) |
| BR-P-08 | Quick Registration and Emergency Registration both fail with an explicit message if the acting staff user has no facility assigned to their account. | HC-PAT-002 AC5, HC-PAT-003 AC5 |
| BR-P-09 | Non-admin staff can only register patients into their own facility (facility scoping applies to write operations, not just reads). | HC-PAT-001 "User Roles and Permissions", NFR-003 |
| BR-P-10 | A registration with zero changed/entered optional data still succeeds as long as the 2–3 mandatory fields for that flow are valid — there is no "minimum richness" requirement beyond the stated mandatory fields. | Derived from BR-P-02/05/06 |
| BR-P-11 | Aadhaar Number, when provided, must be exactly 12 numeric digits, is encrypted at rest, and is never redisplayed in full after save (masked). | HC-PAT-001 Validations, NFR-001 |
| BR-P-12 | The QR code is generated automatically the moment registration succeeds — it is not a separate user action for the initial view (only for later re-retrieval). | HC-PAT-005 AC1 |
| BR-P-13 | ABHA features (OTP, search, link) are **entirely hidden** — no control or data exposed anywhere — unless the ABHA feature flag is on and ABDM credentials are configured. Off by default. | HC-PAT-022 AC4, NFR-008 |
| BR-P-14 | The ABHA OTP itself is never visible to staff at any point — only the patient, on their own device, receives it. | HC-PAT-022 AC3 |
| BR-P-15 | ABHA-prefilled fields (from OTP verification or registry search) remain fully editable before save — national data assists, it does not lock the form. | HC-PAT-023 AC2, HC-PAT-024 AC4 |
| BR-P-16 | No patient record is ever physically deleted by any operation in this module (soft-delete/merge-flag only) — relevant to registration in that **test data created by automation is permanent** unless explicitly reset at the database level. | NFR-005 (cross-reference; deletion itself is out of core scope) |
| BR-P-17 | Photo capture in Step 1 of the Full Wizard is a UI placeholder only in the current build — it does not actually capture/store an image. | Assumptions #7 |
| BR-P-18 | **Known gap:** a second, alias registration-creation function exists in the current build performing the same operation as the canonical wizard function; both must currently remain behavior-identical. | NFR-007 |

## C. Cross-Cutting Rule (Applies to Both Modules)

| # | Rule | Source |
|---|---|---|
| BR-X-01 | Every create/update/delete-equivalent action in both modules is written to an append-only audit trail with the acting user, date, and time — audit entries are never editable or deletable through any screen. | HC-USR NFR-008; HC-PAT NFR-004 |
| BR-X-02 | Both modules require an authenticated session for all in-scope actions except the two explicitly public/unauthenticated Login-adjacent flows: HC-USR-012 (request reset code) and HC-USR-013 (reset with code). | HC-USR-012/013 "User Roles and Permissions"; NFR-002 |
