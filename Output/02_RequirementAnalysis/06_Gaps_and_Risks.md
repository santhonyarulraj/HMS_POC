# 06 — Missing Requirements, Ambiguities, and Automation Risks

---

## A. Missing Requirements

| # | Gap | Impact |
|---|---|---|
| MR-01 | No test environment URL, deployment mode, or network access details exist anywhere in the documentation (carried over from the Documentation Audit — still unresolved). | Blocks all automation until provided. |
| MR-02 | No test/seed credentials for any of the four roles, and no confirmation of whether 2FA can be exempted for a QA account. | Blocks automated login entirely — see Risk AR-01. |
| MR-03 | No test-data seeding specification: which facilities/departments already exist in the target environment, or whether the POC needs to create its own. | Facility-scoped assertions (e.g., "admin sees all facilities") cannot be designed without knowing how many facilities exist. |
| MR-04 | No specification of the exact character-class/format rules behind "valid email format," "valid PIN code," etc. — only that a message exists when the format is wrong. | Boundary-value test cases (e.g., is `+91XXXXXXXXXX` a valid phone entry?) cannot be written precisely. |
| MR-05 | No confirmation of whether embedded visual mockups exist behind the "Screen 1/Screen 2" captions in either FRD (carried over from the Documentation Audit). | Cannot confirm exact field layout/order/labels beyond what the text describes — relevant to `data-testid`/locator strategy. |
| MR-06 | No email-testing mechanism specified for verifying the Forgot-Password OTP email (HC-USR-012/013) in an automated environment. | HC-USR-012/013 cannot be automated end-to-end without one — see Risk AR-03. |
| MR-07 | No TOTP secret provisioning strategy specified for automating 2FA-enabled login (HC-USR-015). | 2FA-gated login cannot be automated end-to-end without one — see Risk AR-02. |
| MR-08 | No confirmation of which of the two "canonical vs. alias" function pairs (HC-USR "Known Gap," HC-PAT NFR-007/Gap 3) the live UI actually routes to by default — the FRDs state a canonical function is intended but note the alias also exists and is currently reachable. | Automation could unintentionally exercise the non-canonical path if the UI doesn't make the distinction visible. |

## B. Ambiguous Requirements

| # | Ambiguity | Why It Matters |
|---|---|---|
| AM-01 | **Scope boundary of "Login"** — does the approved POC scope mean only the authentication experience (this analysis's interpretation, `01_Business_Summary.md` §2.1), or the entire User Management & Authentication FRD including Staff Management, RBAC matrix administration, Facility/Department management, and Audit Trails? | Materially changes the size of Phase 3 (Test Plan) — 10 features vs. 29. |
| AM-02 | **Scope boundary of "Patient Registration"** — does it include Directory/Search/Edit/Delete and the standalone duplicate-merge admin workflow, or only the three registration flows + QR + inline duplicate check + ABHA (this analysis's interpretation, `01_Business_Summary.md` §2.2)? | Materially changes the size of Phase 3 — 10 features vs. 25. |
| AM-03 | **Direct conflict between two source documents on custom roles.** The Login FRD (§1.4, Assumptions #1, and three other places) states unambiguously: *"Exactly four system roles exist... custom role creation is not supported."* The Role Matrix and Permission Catalog document (§3) states: *"Any number of roles can exist — four are seeded by default... and hospital admins can create custom roles through the roles.py router."* These cannot both be true of the same system. | Determines whether test-user-matrix design should plan only for 4 fixed roles or must also handle custom-role creation/assignment. This was found during this analysis, not flagged in either source document. |
| AM-04 | **Current (buggy) vs. specified (ideal) behavior for documented "Known Gaps."** Both FRDs explicitly document defects in the *current build* (e.g., HC-USR-004 unauthenticated account creation; HC-USR-010 sessions not invalidated on password change; HC-PAT edit-alias under-enforcing permissions). The FRDs word the *requirement* as "shall" (implying correct behavior) while separately noting the current build doesn't do that yet. | Automated tests must target one or the other — asserting the "shall" statement against a system that is documented as not yet doing it will produce a failing test that is not an automation bug. Needs an explicit decision before Test Plan. |
| AM-05 | HC-USR-020 (facility edit, out of core scope) operates on "the current facility" with no ID parameter, and how an admin switches "current facility" context is not described anywhere in the FRD. Flagged for completeness in case facility-context switching becomes relevant to in-scope facility-scoped registration tests. | Could affect how multi-facility test scenarios are set up, even though the feature itself is out of scope. |
| AM-06 | HC-PAT-025 (ABHA link for an *existing* patient) is grouped under "ABHA-Assisted **Registration**" in the source FRD's section heading, but its own acceptance criteria describe it acting on an already-registered patient's record after the fact — closer to a profile-management action than a registration-time action. | Affects whether HC-PAT-025 belongs in this POC's in-scope list at all (see `01_Business_Summary.md` §2.2, listed in-scope for now, flagged here for confirmation). |

## C. Automation Risks

| # | Risk | Detail |
|---|---|---|
| AR-01 | **2FA may block fully automated login.** If a test account has 2FA enabled or belongs to a role with enforcement ON (default: admin), Playwright cannot proceed past HC-USR-015 without either (a) a way to disable/exempt 2FA for QA accounts, or (b) the TOTP secret to generate valid codes programmatically (e.g., via `otplib`). Neither is currently available. | High — blocks admin-role login entirely under default configuration. |
| AR-02 | **2FA setup/verify cannot be end-to-end automated without a provisioned TOTP secret.** Even for non-enforced roles, testing HC-USR-014/015 as positive-path scenarios requires generating valid 6-digit codes in-test, which requires knowing the secret at enrollment time. | Medium — affects only the 2FA-specific test scenarios, not general login. |
| AR-03 | **Forgot-Password (HC-USR-012/013) requires reading a real inbox.** The OTP is delivered by email only. No test-mailbox strategy (e.g., Ethereal, Mailosaur, a shared IMAP test account) is currently defined. | Medium — blocks this specific flow only. |
| AR-04 | **Session cookie cannot be read or forged by test code** (httpOnly/Secure/SameSite=Strict, per NFR-001). All authenticated-session setup must go through either a real UI login or a supported API login call whose response Playwright's browser context can accept as a cookie — the existence of a documented API login endpoint is not confirmed. | Medium — affects test speed/design (`storageState` reuse pattern), not feasibility. |
| AR-05 | **Rate limiting could self-block CI.** 5 login attempts/minute per source address (BR-L-05) means negative-path login tests (wrong password, etc.) run too close together — or run repeatedly from the same CI runner IP across parallel jobs — risk tripping the same lockout a real attacker would trigger, blocking subsequent legitimate test runs. | Medium — needs pacing/isolation strategy in Test Plan. |
| AR-06 | **Soft-delete-only data model means test data is permanent.** Every patient created by automation (Full Wizard, Quick, Emergency) remains in the database forever — there is no hard-delete path anywhere in scope. Repeated CI runs will accumulate patients indefinitely and, worse, may begin *triggering the duplicate-detection warning/block logic (BR-P-04)* against each other over time. | Medium-High — needs a dedicated test facility, a naming convention for automation-created patients, and/or a database-level reset strategy between runs (none of which currently exist). |
| AR-07 | **UHID and QR code are only known after the fact.** Both are server-generated at the moment of successful registration — tests must capture them dynamically from the success screen/response rather than hardcoding expected values, and any assertion depending on UHID *format* (not value) should test the pattern, not a literal string. | Low — standard automation pattern, just needs to be designed for from the start. |
| AR-08 | **Known Gaps may cause "expected" test failures.** Per AM-04, several FRD "shall" statements describe intended behavior the current build does not yet implement. Any test asserting the FRD's ideal behavior for one of these (e.g., asserting other sessions are invalidated after a password change) will fail against the real system — correctly, but for reasons unrelated to the automation itself. | High — must be resolved (which ground truth to test against) before Test Plan, or every subsequent test run will contain confusing "failures" that are actually pre-known product behavior. |
| AR-09 | **ABHA flows depend on an external national registry (ABDM).** Real end-to-end testing of HC-PAT-022–025 requires either live ABDM sandbox access or a mock/stub — neither is confirmed available, and the feature is off by default anyway (BR-P-13). | Medium — likely candidate to defer or stub, pending client input. |
| AR-10 | **Facility-scoping assertions need ≥2 seeded facilities** to meaningfully test cross-facility isolation (e.g., non-admin cannot see/register into a facility they don't belong to). If the test environment has only one facility, this class of test cannot be exercised at all. | Low-Medium — depends on MR-03 being resolved. |

## D. Priority Note

The single highest-priority item across this document is **AM-04 / AR-08** (current vs. specified behavior for documented gaps) combined with **MR-01/MR-02** (no environment or credentials) — nothing in Phase 3 (Test Plan) can be scoped realistically until these are resolved. See `07_Client_Questions.md` for the consolidated question list.
