# 05 — Assumptions and System Dependencies

**Note on method:** per instruction, this analysis does not invent assumptions to fill gaps — anything genuinely unclear is routed to `06_Gaps_and_Risks.md` or `07_Client_Questions.md` instead. The items below are assumptions/constraints **already stated as verified fact inside the source FRDs themselves**; they are reproduced here (not newly asserted) because automation design will depend on them.

---

## A. Assumptions Carried From the Login FRD (§4, verified in source)

1. Only four system roles exist (admin, doctor, receptionist, pharmacist); custom role creation is not implemented anywhere in the system *(see `06_Gaps_and_Risks.md` — this directly conflicts with a statement in the Role Matrix and Permission Catalog document)*.
2. Non-admin staff can see all staff of their own facility in the staff list — verified behavior, not a defect *(out of core scope, listed for completeness since it affects the RBAC mental model)*.
3. Session activity is a last-login summary only; there is no live per-session tracking, device detail, or per-session revoke in this release *(out of core scope feature, but relevant context: automation cannot assert on live session lists)*.
4. Password reset codes are delivered by email only — no SMS/WhatsApp, no clickable link. Delivery depends on SMTP configuration owned by the out-of-scope Admin Settings FRD (HC-ADS-018).
5. The second factor follows the TOTP standard with a 30-second step and ±1 step tolerance (effective ~90-second acceptance window).
6. Permission and role changes take effect at the affected user's **next login** — not immediately — because the permission map loads at login time and is cached for the session.
7. The audit CSV export is capped at 10,000 records *(out of core scope)*.
8. 2FA enforcement flags live in the `security_settings` key-value store, while the Admin Settings security panel (HC-ADS-024, out of scope) saves numeric policy values (lockout duration, session timeout, password expiry) to a different `settings` category. Until engineering reconciles the two stores, any divergence between them is itself a defect.
9. Feature flags are per-facility and owned entirely by the out-of-scope Admin Settings FRD (HC-ADS-016).
10. Deleting data never removes audit history — audit trails retain references to deleted users/records even after the underlying record is gone.

## B. Assumptions Carried From the Patient FRD (§4, verified in source)

1. UHID format `PAT+YYMM+XXXX` is auto-generated by the system per facility; any on-screen preview before creation is display-only and is never itself stored.
2. An earlier (superseded) document described patient deletion as setting a status field to "Inactive" — the *verified* current mechanism is a merge-flag + note ("Deleted by administrator"), surfaced on screen as a "Deleted" status. *(Relevant context even though HC-PAT-016 itself is out of core scope, because it explains why deleted test patients are never truly gone.)*
3. Duplicate-phone handling is **intentionally different** between the Full Wizard (warn + allow override) and Quick Registration (hard block) — both are verified, deliberate behaviors, not an inconsistency to "fix."
4. Duplicate detection logic (phone/name-similarity/DOB matching) runs system-side on a schedule or on demand; the FRD specifies the review-and-resolve workflow, not the matching algorithm itself *(the review/resolve workflow, HC-PAT-018 to 021, is itself out of core scope)*.
5. ABHA integration requires the ABHA feature flag ON and valid ABDM credentials configured (both owned by the out-of-scope Admin Settings FRD); **off by default**.
6. Photo capture in registration Step 1 is a UI placeholder only in the current version — no actual image capture/storage occurs.
7. Emergency registrations intentionally capture only the minimum needed for immediate care; full profile completion happens later through Edit (HC-PAT-015, out of core scope).

## C. System Dependencies

### C.1 Dependencies on Out-of-Scope Documents/Modules

These are **hard dependencies** the in-scope features have on the Admin Settings FRD, which this POC has explicitly excluded. Automated tests touching these areas will be exercising configuration this analysis has not reviewed:

| In-Scope Feature | Depends On | Owned By (out of scope) |
|---|---|---|
| Login lockout duration, session timeout, password expiry days, attempt limits | Numeric security policy values | Admin Settings FRD, HC-ADS-024 |
| Forgot Password email delivery (HC-USR-012) | SMTP configuration | Admin Settings FRD, HC-ADS-018 |
| ABHA OTP/search/link (HC-PAT-022–025) | ABHA feature flag + ABDM credentials | Admin Settings FRD, HC-ADS-016, HC-ADS-012 |

### C.2 Technical/Architectural Dependencies (from Solution Architecture Document)

- **Session mechanism:** JWT issued at login (`backend/auth.py`), delivered via a secure `httpOnly`/`Secure`/`SameSite=Strict` cookie — **not** accessible to browser-side JavaScript. Any automation strategy that tries to read/inject a session token directly (rather than driving the real login UI or using a supported API login call) will not work against this architecture.
- **Backend:** FastAPI (Python), single PostgreSQL database, no ORM (raw parameterized SQL via psycopg2). Relevant if API-level test-data seeding is later considered.
- **Facility scoping:** enforced server-side via `facility_id` on nearly every table — not just a UI filter. Test users must have a correctly assigned facility for facility-scoped assertions (e.g., "non-admin sees only their facility's patients") to be meaningful.
- **Deployment mode:** a single running instance is either `onpremise` or `saas`, never both — determined by the `DEPLOYMENT_MODE` environment variable. Which mode the POC's test environment runs in is not yet known (see `07_Client_Questions.md`).
- **No WebSockets:** the frontend polls (Axios/TanStack Query) rather than pushing live updates — relevant to HC-PAT-004 (Active Emergencies List auto-refresh), which is polling-based, not real-time-pushed.

### C.3 Inter-Module Dependency Within Scope

- HC-PAT-001 Step 5 (ID & Insurance) directly invokes HC-PAT-022–024 (ABHA) inline — these cannot be tested in complete isolation from the wizard if ABHA is in scope.
- HC-USR-001 (Login) is a hard precondition for every Patient Registration feature — no registration flow is reachable without an authenticated session first.
- HC-USR-015 (2FA Verify) is conditionally invoked from within HC-USR-001 (Login) — not a separate entry point.
