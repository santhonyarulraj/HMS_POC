## A. Login — Business Rules (21)

| ID | Rule | Source |
|---|---|---|
| BR-L-01 | Exactly four system roles exist: admin, doctor, receptionist, pharmacist. Custom role creation is **not** supported. | HC-USR §1.4, Assumptions #1 — **see `09_Requirement_Conflicts.md`, CONFLICT-001** |
| BR-L-02 | A deactivated account cannot log in, regardless of correct credentials. | HC-USR-001 AC5 |
| BR-L-03 | An account flagged for forced password reset is redirected to Change Password before the dashboard opens, on every login until the flag clears. | HC-USR-001 AC6, HC-USR-010 AC4 |
| BR-L-04 | If 2FA is enabled on the account, or enforced for the account's role, the second factor is required before the session is granted — no exceptions. | HC-USR-001 AC7 |
| BR-L-05 | Login attempts are rate-limited to 5 per minute per source address. | HC-USR-001 AC9, NFR-003 |
| BR-L-06 | The invalid-credentials error message never discloses whether the username or the password was wrong. | HC-USR-001 AC10 |
| BR-L-07 | Logout invalidates the session server-side immediately; a replayed (already-invalidated) session credential is refused on any subsequent request. | HC-USR-002 AC2/AC5, NFR-004 |
| BR-L-08 | Password complexity policy (every password-set operation: change, admin temp-set, reset-with-code): minimum 8 characters, ≥1 uppercase, ≥1 digit, ≥1 special character. | HC-USR-010/011/013, §3.3 |
| BR-L-09 | Changing your own password clears any forced-reset flag on the account. | HC-USR-010 AC4 |
| BR-L-10 | **Known gap:** a password change does not invalidate the user's other active sessions in the current build. | HC-USR-010 AC6, §3.2 Gap 2 |
| BR-L-11 | Forgot-password codes are delivered by email only — never SMS, WhatsApp, or a clickable link. | HC-USR-012 AC4, Assumptions #4 |
| BR-L-12 | Forgot-password codes are valid for 15 minutes and usable exactly once. | HC-USR-012 AC5, HC-USR-013 AC2 |
| BR-L-13 | The forgot-password confirmation message is identical whether or not the submitted username/email actually exists. | HC-USR-012 AC6 |
| BR-L-14 | 2FA setup is not complete until the user proves possession of the paired app with a valid 6-digit code. | HC-USR-014 AC3 |
| BR-L-15 | 2FA issues exactly 8 single-use backup codes at setup; each is consumed the moment it is used. | HC-USR-014 AC5, HC-USR-015 AC3 |
| BR-L-16 | TOTP codes are accepted with a tolerance of one 30-second time-step either side (effective ~90-second window). | HC-USR-015 AC2, Assumptions #5 |
| BR-L-17 | 5 consecutive failed 2FA attempts locks the account for 15 minutes. | HC-USR-015 AC5, NFR-003 |
| BR-L-18 | Default 2FA enforcement: admin = ON; doctor, receptionist, pharmacist = OFF. | HC-USR-017 AC4 |
| BR-L-19 | Session credential (JWT) is held only in a secure, httpOnly, `Secure`, `SameSite=Strict` cookie — never readable by browser-side scripts. | NFR-001 |
| BR-L-20 | Passwords are stored only as one-way hashes (bcrypt, cost factor 12); plain text is never stored, logged, or returned. | NFR-002 |
| BR-L-21 | **Known gap:** account creation (HC-USR-004, out of core scope) is currently callable without authentication. | §3.2 Gap 1 |

## B. Patient Registration — Business Rules (18)

| ID | Rule | Source |
|---|---|---|
| BR-P-01 | UHID format is fixed: `PAT` + `YYMM` + 4-digit sequence, auto-generated by the system, unique per facility. Never user-entered. | HC-PAT-001 AC9, Assumptions #1 |
| BR-P-02 | In the Full Wizard, only First Name, Last Name, and Phone are truly mandatory — every other field across all 7 steps is optional. | HC-PAT-001, UI Schema (Table 7) |
| BR-P-03 | In the Full Wizard, the user cannot advance past a step while a mandatory field on that step is invalid. | HC-PAT-001 AC10 |
| BR-P-04 | **Duplicate-phone handling differs by design between flows:** Full Wizard warns and allows override; Quick Registration blocks outright. | HC-PAT-017, HC-PAT-002 AC3, Assumptions #3 |
| BR-P-05 | Quick Registration mandatory fields: First Name, Last Name, Phone. DOB and Gender optional. | HC-PAT-002, UI Schema (Table 10) |
| BR-P-06 | Emergency Registration mandatory fields: Patient Name ("Unknown" explicitly permitted) and Chief Complaint. Phone optional. | HC-PAT-003 AC2/AC3, Validations (Table 14) |
| BR-P-07 | Emergency Registration defaults Triage Priority to P2 when not specified. | HC-PAT-003, UI Schema (Table 13) |
| BR-P-08 | Quick and Emergency Registration both fail with an explicit message if the acting user has no facility assigned. | HC-PAT-002 AC5, HC-PAT-003 AC5 |
| BR-P-09 | Non-admin staff can only register patients into their own facility. | HC-PAT-001 "User Roles and Permissions", NFR-003 |
| BR-P-10 | A registration with zero optional data still succeeds as long as the mandatory fields for that flow are valid. | Derived from BR-P-02/05/06 |
| BR-P-11 | Aadhaar Number, when provided, must be exactly 12 numeric digits, is encrypted at rest, and is never redisplayed in full after save. | HC-PAT-001 Validations, NFR-001 |
| BR-P-12 | The QR code is generated automatically the moment registration succeeds. | HC-PAT-005 AC1 |
| BR-P-13 | ABHA features are entirely hidden unless the ABHA feature flag is on and ABDM credentials are configured. Off by default. | HC-PAT-022 AC4, NFR-008 |
| BR-P-14 | The ABHA OTP itself is never visible to staff at any point. | HC-PAT-022 AC3 |
| BR-P-15 | ABHA-prefilled fields remain fully editable before save. | HC-PAT-023 AC2, HC-PAT-024 AC4 |
| BR-P-16 | No patient record is ever physically deleted by any operation in this module (soft-delete/merge-flag only). | NFR-005 (cross-reference; deletion feature itself out of core scope) |
| BR-P-17 | Photo capture in Step 1 of the Full Wizard is a UI placeholder only — it does not capture/store an image. | Assumptions #7 |
| BR-P-18 | **Known gap:** a second, alias registration-creation function exists performing the same operation as the canonical wizard function. | NFR-007 |

## Rules Explicitly Flagged as "Known Gaps" (Current Behavior ≠ Ideal Specification)

These 3 rules describe *documented current defects*, not aspirational requirements — Test Planning must decide (per Blocking Question Q3) whether to assert current or ideal behavior for each:

- **BR-L-10** — password change doesn't invalidate other sessions
- **BR-L-21** — account creation currently lacks auth enforcement *(note: this rule concerns HC-USR-004, which is outside the approved requirement scope in §A of `03_Approved_Requirements.md` — retained here for completeness only)*
- **BR-P-18** — canonical vs. alias registration-creation function pair
