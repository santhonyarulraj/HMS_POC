## A. Assumptions — Login FRD (10)

| ID | Assumption |
|---|---|
| ASM-LOG-01 | Only four system roles exist (admin, doctor, receptionist, pharmacist); custom role creation is not implemented anywhere in the system *(directly conflicts with the Role Matrix document — see `09_Requirement_Conflicts.md`, CONFLICT-001)*. |
| ASM-LOG-02 | Non-admin staff can see all staff of their own facility in the staff list — verified behavior, not a defect. |
| ASM-LOG-03 | Session activity is a last-login summary only; no live per-session tracking, device detail, or per-session revoke. |
| ASM-LOG-04 | Password reset codes are delivered by email only — no SMS/WhatsApp, no clickable link. Delivery depends on SMTP configuration owned by the out-of-scope Admin Settings FRD (HC-ADS-018). |
| ASM-LOG-05 | The second factor follows the TOTP standard with a 30-second step and ±1 step tolerance. |
| ASM-LOG-06 | Permission and role changes take effect at the affected user's next login — not immediately. |
| ASM-LOG-07 | The audit CSV export is capped at 10,000 records. |
| ASM-LOG-08 | 2FA enforcement flags live in the `security_settings` key-value store, while numeric policy values live in a different `settings` category owned by the out-of-scope Admin Settings FRD — any divergence between the two is itself a defect. |
| ASM-LOG-09 | Feature flags are per-facility and owned entirely by the out-of-scope Admin Settings FRD (HC-ADS-016). |
| ASM-LOG-10 | Deleting data never removes audit history. |

## B. Assumptions — Patient Registration FRD (7)

| ID | Assumption |
|---|---|
| ASM-PAT-01 | UHID format `PAT+YYMM+XXXX` is auto-generated by the system per facility; any on-screen preview before creation is display-only. |
| ASM-PAT-02 | The verified patient-deletion mechanism is a merge-flag + note ("Deleted by administrator"), surfaced on screen as a "Deleted" status — superseding an earlier document's "Inactive" description. |
| ASM-PAT-03 | Duplicate-phone handling is intentionally different between the Full Wizard (warn) and Quick Registration (block) — both deliberate, verified behaviors. |
| ASM-PAT-04 | Duplicate detection logic (phone/name-similarity/DOB) runs system-side on a schedule or on demand; the FRD specifies the review-and-resolve workflow, not the matching algorithm. |
| ASM-PAT-05 | ABHA integration requires the ABHA feature flag ON and valid ABDM credentials configured (both owned by the out-of-scope Admin Settings FRD); off by default. |
| ASM-PAT-06 | Photo capture in registration Step 1 is a UI placeholder only — no actual image capture/storage occurs. |
| ASM-PAT-07 | Emergency registrations intentionally capture only the minimum needed for immediate care; full profile completion happens later (out of core scope). |

### C.2 Technical/Architectural Dependencies

| ID | Dependency |
|---|---|
| DEP-04 | Session mechanism is JWT via a secure httpOnly/Secure/SameSite=Strict cookie — not accessible to browser-side JavaScript. |
| DEP-05 | Backend is FastAPI (Python) with a single PostgreSQL database, no ORM (raw parameterized SQL). |
| DEP-06 | Facility scoping is enforced server-side via `facility_id` on nearly every table — not just a UI filter. |
| DEP-07 | Deployment mode (`onpremise` vs. `saas`) is fixed per running instance via the `DEPLOYMENT_MODE` environment variable — not yet known for the POC's test environment. |
| DEP-08 | The frontend polls (Axios/TanStack Query) rather than pushing live updates — relevant to REQ-PAT-004's auto-refresh behavior. |
